# v3.1 프로토타입 프론트–백엔드 계약

상태: `CORE IMPLEMENTED / REAL DATA INPUT REQUIRED`  
기존 구현 계약: `frontend-backend-contract.md`

이 문서는 실제 데이터 프로토타입의 추가 계약이다. 개별 메뉴·서버 계산·실데이터 반입 모델은 생성 OpenAPI와 프론트 타입에 반영되어 있다. 실제 입력 자료가 들어오면 같은 순서로 계약과 인수 검사를 갱신한다.

## 핵심 흐름

1. 자연어 입력을 `/api/parse-query`가 조건 초안으로 변환한다.
2. 인원 또는 예산의 종류·금액이 모호하면 `confirmation_required`에 넣고 추천을 호출하지 않는다.
3. 사용자가 확정한 조건과 현재 `snapshot_id`로 `/api/recommendations`를 호출한다.
4. 서버는 실제 장소·개별 메뉴 가격·행동 집계 근거를 조회하고 가격·총액·예산 상태를 코드로 계산한다.
5. 프론트가 조건을 바꾸면 이전 추천·상세·예산 결과와 선택 목록을 즉시 무효화한다.
6. 정보 부족 후보는 정상 추천과 분리하고, 누락값을 0 또는 추정 실측값으로 표시하지 않는다.

## 세 화면으로 묶는 표시 계약

| 화면 | 포함 기능 | API |
|---|---|---|
| 1. 입력·확인 | 자연어, 파싱 결과, 지역·업종·인원·예산·목적 확인 | `GET /api/meta`, `POST /api/parse-query` |
| 2. 추천 | 실제 장소 목록, 메뉴 기준 예상 지출, 예산 상태, 추천 이유, 출처 기준일 | `POST /api/recommendations` |
| 3. 근거·비교 | 선택 장소의 메뉴 항목, 계산식, 상권 집계 근거, 대안별 예산 | `GET /api/places/{id}`, `POST /api/budget/estimate` |

React 내부 상태는 세부 기능을 위해 유지하지만 사용자가 보는 상단 동선과 단계 표시는 위 3단계로 고정했다.

## 실제 데이터 응답에 필요한 추가 필드

가격 근거에는 범위뿐 아니라 계산에 사용한 메뉴가 필요하다.

```json
{
  "menu_items": [
    {
      "menu_item_id": "stable-id",
      "name": "메뉴명",
      "price_krw": 12000,
      "quantity": 2,
      "unit": "1인분",
      "source_id": "source-id",
      "observed_at": "2026-09-19",
      "is_mock": false
    }
  ],
  "calculation": {
    "party_size": 2,
    "total_min": 24000,
    "total_max": 24000,
    "budget_status": "fits"
  }
}
```

실제 구현은 `price.menu_items`와 `budget.items[].menu_calculations`로 제공한다. 현재 지원하는 주문 단위는 `per_person`이며 `min_order_qty`를 반영한다. 세트·공유 메뉴 단위는 실제 입력 자료가 필요할 때 별도 계약으로 확장한다.

## 상태 변경 규칙

- `region_id`, `category`, `purpose`, `party_size`, `budget`, `visit_at` 또는 필수 분위기가 바뀌면 이전 파생 결과를 사용하지 않는다.
- 진행 중 요청도 버전이 지난 응답이면 버린다.
- 결과/상세/예산 단계는 선행 데이터가 있을 때만 이동 가능하다.
- 새 조건으로 추천을 다시 실행해야 최신 계산 결과를 표시한다.

## AI 경계

- Gemini: 조건 구조화와 근거 문장 초안에만 사용한다.
- 서버 코드: 메뉴 선택 규칙, 수량, 합계, 1인당 금액, 잔액, 예산 초과 판정, 추천 필터.
- Gemini 결과는 서버 스키마 검증 후 사용하며 출처·가격·행동 지표를 새로 만들어 내지 못한다.
- 실패·timeout·권한 오류 때 규칙 파서로 대체할 수 있지만, 그 실행은 `parser_mode=rules`로 정직하게 표시한다.

## 완료 판정 시나리오

- 명시 조건: 지역·업종·2명·인당 예산·목적을 파싱하고 사용자가 확인한다.
- 모호 조건: “둘이 4만원”처럼 1인당/총액이 불명확하면 확인 전 추천을 막는다.
- 재계산: 예산을 바꾸면 이전 결과가 사라지고 새 서버 계산 결과가 나온다.
- 예산 초과: 실제 메뉴 합계가 초과인 후보를 `exceeds`로 표시하거나 정책대로 제외한다.
- 정보 부족: 메뉴 또는 출처가 불충분한 장소를 정상 추천으로 위장하지 않는다.
- 실제 근거: 실제 장소·메뉴·행동 집계의 출처와 기준일을 화면에서 확인한다.
- 실제 AI: `parser_mode=gemini`인 요청을 실호출하고 오류 대체 경로도 검증한다.
